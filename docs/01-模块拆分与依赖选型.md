# 01 · 模块拆分与依赖选型

> 本文回答两个问题：**每个模块用了什么现成的轮子、为什么**；以及**哪些代码是自研的、为什么不能用现成的**。
> 版本号均取自仓库中的 `Cargo.lock` / `app/pubspec.lock`（锁定版本，构建可复现）。

## 1. 总体架构

```
┌──────────────────────── 客户端（信任域：明文只在此存在） ────────────────────────┐
│ Flutter UI（Windows / macOS / Android / iOS 同一套 Dart 代码）                   │
│   app/lib/src/{ui,state,core}                                                    │
│        │  flutter_rust_bridge 2（自动生成绑定，app/lib/src/rust/**）              │
│ vaultone_bridge（app/rust）── Dart 可见 API、日志、剪贴板                        │
│        │                                                                         │
│ vault-core ── 保险库 / 本地 SQLite / 同步客户端 / 三方合并 / URL 匹配 / TOTP / 审计│
│ vault-crypto ── AES-256-GCM 密封盒 / Argon2id 双因子派生 / SRP-6a / 受保护内存   │
│ vault-proto ── 与服务端共享的线协议（仅密文与元数据）                            │
│ 浏览器扩展（extension/）⇄ vault-nmhost（Native Messaging 转发）⇄ 本地套接字 ⇄ 桌面端│
└──────────────────────────────────┬──────────────────────────────────────────────┘
                                   │ HTTPS（rustls）· 只传输密文 + 版本号 + 时间戳
┌──────────────────────────────────▼──────────────────────────────────────────────┐
│ vault-server（axum）：SRP-6a 认证 · 设备批准 · 增量同步 · 恢复 · 审计 · 邮件      │
│ sqlx Any：SQLite（内测/单机）或 PostgreSQL 16（生产）· Caddy 反代自动 HTTPS       │
└─────────────────────────────────────────────────────────────────────────────────┘
```

与计划书 §3.3 的差异（均为有意取舍，已在 CLAUDE.md 记录）：

| 计划书 | 实际 | 理由 |
|---|---|---|
| Tauri 桌面 + Swift/Kotlin 原生移动端 | **Flutter 一套 UI 覆盖 4 端** + Rust 内核 | 9 人团队 → 本仓库以最小人力覆盖全平台；密码学仍全部在 Rust 内核，UI 层零密钥逻辑 |
| Go 服务端 | **Rust（axum）服务端** | 与客户端共享 `vault-crypto` / `vault-proto`，协议与 SRP 实现只有一份，杜绝两端不一致 |
| XChaCha20-Poly1305 / AES-256-KW | **统一 AES-256-GCM 密封盒** | 满足本次交付的加密规范（全部敏感数据统一 AES-256-GCM、随机 IV、随机盐） |
| SQLCipher | SQLite + **应用层逐字段 AES-256-GCM** | 本地库中除非敏感元数据外全部是密封盒；SQLCipher 需 OpenSSL 交叉编译 5 个平台，收益有限（见 docs/03 §6） |
| Redis 会话/限流 | 会话存数据库（token 哈希）、限流用进程内 `governor` | MVP 单实例足够；SRP 握手状态加密后存库，已支持多实例水平扩展 |

## 3. 自研代码（仅限核心创新）及其不可替代性

除下列 4 项外，仓库中其余自研代码都是「把成熟库按固定规则组合」的胶水与业务流程。

### 3.1 零知识字段级三方合并（`crates/vault-core/src/merge.rs`）

- **问题**：E2EE 同步中服务端看不到明文，无法像普通同步服务那样在服务端合并；常见 E2EE 同步方案对并发编辑采用「整条目后写覆盖」，两台设备离线分别修改同一条目的不同字段时，一方的修改被静默丢弃（违反计划书 F-06/A-05）。
- **做法**：客户端为每个条目保留「最后一次与服务端一致的密文」（base），冲突时在本地解密 base / local / remote 三个版本，逐字段三方合并；双方都改的字段取 `updated_at` 较新者；被覆盖的旧密码自动进入 `passwordHistory`，保证「最新修改 + 保留历史版本」。
- **不可替代性**：通用 CRDT / diff 库（automerge、yrs）要求把操作日志交给同步端或改变数据模型，与「服务端只存不可解析的密文块」相冲突；本算法只在客户端内存运行，不引入新的密码学构造，服务端协议无需任何改动。
- **验证**：`merge.rs` 6 个单元测试 + `vault-server/tests/e2e.rs::full_lifecycle` 中双设备并发编辑不同字段、双方修改均保留。

### 3.2 防钓鱼自动填充匹配策略（`crates/vault-core/src/urlmatch.rs`）

- 公共后缀判定完全复用 `psl`；自研的是**匹配策略**：协议降级拒绝（https 条目不在 http 页面匹配）、IP/单标签主机禁止放宽、未收录公共后缀不放宽、punycode 比较抵御同形异义字、Exact > Host > Domain 打分排序。
- **不可替代性**：现有库只回答「这个域名的注册域是什么」，不回答「这个页面能否安全地填充这条凭据」；后者是密码管理器的核心安全决策（计划书 S-06 / B-06），必须由产品自己定义并测试。
- **验证**：7 个单元测试，覆盖 github.io 私有后缀、SSL strip、西里尔字母 а 仿冒、IP 端口不同等钓鱼场景。

### 3.3 AES-256-GCM「密封盒」格式与密钥层级编排（`crates/vault-crypto/src/sealed.rs`、`kdf.rs`）

- 原语全部来自 RustCrypto；自研的是**格式与组合规则**：每次加密随机 32 字节盐 + 12 字节 IV，经 HKDF 派生一次性消息密钥，头部（版本、套件、盐、IV）纳入 GCM 认证；主密码 × Secret Key 双因子派生（2SKD）。
- **不可替代性**：没有现成库同时满足「统一 AES-256-GCM、每次随机 IV、每次随机盐、盐与 IV 随密文存储并受认证、可版本演进」这组约束；`age`、`libsodium sealed box` 分别绑定 X25519/ChaCha20，不符合规范。
- **优势**：每条消息使用由随机盐派生的一次性子密钥，彻底消除同一长期密钥下 96-bit 随机 IV 的生日界（2^32 条消息）风险。
- **验证**：逐字节篡改检测、AAD 边界、已知答案复算（第三方可按 `docs/03` 独立实现解密）等 8 个测试。

### 3.4 浏览器扩展配对与请求认证（`crates/vault-core/src/browser.rs`）

- 原语是 HMAC-SHA256 与 SHA-256；自研的是**协议**：扩展生成 256-bit 配对密钥，桌面端显示由其派生的 8 位配对码供用户核对后批准；此后每个请求带 `HMAC(密钥, 域分隔‖clientId‖nonce‖ts‖body)`，±120 s 时间窗 + nonce 去重防重放；配对密钥以 Vault Key 密封存储，锁定时一律返回 `locked`。
- **不可替代性**：Native Messaging 只保证"是某个浏览器扩展在调用"，不保证是**本用户批准过的**扩展，也挡不住同机其他进程直连本地套接字；现成密码管理器的做法都绑定在各自产品里，没有可复用的库。释放凭据前还要经过 §3.2 的 URL 匹配，扩展即使被攻破也只能拿到当前页面匹配的那一条。
- **验证**：`browser.rs` 7 个单元测试（重放、错误密钥、过期时间戳、钓鱼域名拒绝、保存 / 更新、与 JS 实现的固定交叉向量）；`app/rust/src/api/browser.rs` 在真实本地套接字上、并经真实宿主进程转发的端到端测试。
