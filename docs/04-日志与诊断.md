# 04 · 日志与诊断

> 规定客户端与服务端「记什么、不记什么、放在哪、留多久」。文档与代码冲突时以代码为准。

## 1. 客户端日志 —— `app/rust/src/api/logging.rs`

| 项 | 规则 |
|---|---|
| 框架 | `tracing` + `tracing-appender`，非阻塞写入 |
| 位置 | 应用支持目录（`getApplicationSupportDirectory`）下 `logs/vaultone.YYYY-MM-DD.log`（目录由 `main.dart` 创建） |
| 轮转 | 按天滚动，保留 7 个文件 |
| 级别 | 默认 `info`；「设置 → 诊断 → 详细日志（诊断模式）」开启后为 `debug`（重启生效；只作用于下行列出的目标，其余目标固定 `warn`） |
| 目标 | `vault_core` / `vaultone_bridge` / `vault` / `sync` / `bridge` / `ui`（Dart 侧经 `log_event` 写入）/ `browser`（浏览器扩展通道：配对、凭据释放、拒绝的请求，均不含网址与凭据）按上行级别输出 |
| 获取 | 仅桌面端（Windows / macOS / Linux）有「设置 → 诊断 → 日志文件 → 打开目录」入口，由用户自行附到反馈中；移动端当前无应用内导出入口。应用**不会自动上传** |

## 2. 服务端日志 —— `crates/vault-server/src/{main,lib}.rs`

- 格式：`log_format = "pretty"`（开发）或 `"json"`（生产，便于日志平台采集）；级别由 `log_level` 或 `VAULTONE_LOG`（`EnvFilter` 语法）控制。
- 访问日志：每个请求一个 `http` span（`tower_http::trace::TraceLayer`），字段只有 `method`、`path`（不含查询串）与 `request_id`。`x-request-id` 请求未携带时由服务端生成 UUID，并回写到响应头，便于用户报障时对照。状态码与耗时由 tower-http 默认的响应事件记录，级别为 `debug`（默认 `log_level = "info"` 下不输出，需加 `tower_http=debug`）；5xx 以 `error` 级别记录。**不记录**请求体、查询串与 `Authorization` 头。
- 业务日志以 `user` 字段（即 account_id，UUID）标识用户；邮箱只在 `mail.mode=log` 时以脱敏形式出现（`a***@example.com`，`mail::mask`）。注意 `log` 模式会把邮件正文（含新设备验证码）原样写入日志，仅限开发环境。
- 审计事件单独入库（`audit_events` 表：事件名、设备 ID、IP 的 16 字节 HMAC、时间），用户开启云同步后可在客户端「设置 → 云同步 → 安全日志」查看最近 100 条（`GET /v1/audit`）；账户注销时一并删除。

## 3. 绝不记录的内容（客户端与服务端通用）

| 类别 | 说明 |
|---|---|
| 主密码 / Secret Key / 恢复码 | 任何形式都不记录，包括哈希 |
| 派生密钥与会话 token | `Key32` 的 `Debug` 输出为 `Key32(<redacted>)`；服务端只存 token 的 SHA-256 |
| 条目内容 | 标题、用户名、密码、URL、备注、TOTP 密钥（合并冲突日志只记字段名，不记字段值） |
| 邮箱明文 | 仅 `mail.mode=log` 下以脱敏形式出现 |
| panic 负载 | 客户端 panic hook 只记录源码位置（`file:line`），不记录消息内容，因为消息可能携带数据。服务端 `CatchPanicLayer` 只记录 `handler panicked` 并返回 500，但**未替换** Rust 默认 panic hook，默认 hook 仍会把 panic 消息打印到 stderr |

新增日志语句时按上表自查；评审时对 `tracing::` 调用中出现的字段逐一确认不属于上表。

## 4. 排障流程

1. 用户在「设置 → 诊断」开启详细日志，重启应用后复现问题；
2. 桌面端经「打开目录」找到日志目录，将当天日志文件随工单提交（文件中不含上表内容，可直接转交）；
3. 若涉及同步错误：客户端在详细日志下为每个请求记录方法、路径、状态码与耗时（`target=sync`，`debug` 级别），**不记录** `x-request-id`。因此只能按时间、路径与状态码在服务端 JSON 日志中检索同一请求，再用服务端日志里的 `request_id` 串联该请求的其他事件。
