# 05 · 部署与运维

> 同步服务 `vault-server` 的部署、配置、备份与密钥管理。部署文件见 `deploy/`。文档与代码冲突时以代码为准。

## 1. 部署形态

内测期单机部署：PostgreSQL 16 + `vault-server` + Caddy（自动 HTTPS），见 `deploy/docker-compose.yml`。

```bash
cp deploy/.env.example deploy/.env        # 填写域名、数据库密码、服务端主密钥、SMTP
docker build -f deploy/Dockerfile -t vaultone/server:1.0.0 .   # 先在本地构建镜像（compose 也用这个 tag）
docker run --rm vaultone/server:1.0.0 gen-secret   # 生成 VAULTONE_SERVER_SECRET（也可 cargo run -p vault-server -- gen-secret）
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d
```

- `.env` 中 `POSTGRES_PASSWORD`、`VAULTONE_SERVER_SECRET`、`VAULTONE_DOMAIN` 为必填（compose 用 `${VAR:?}` 校验，缺失即拒绝启动）。因此须先生成主密钥再执行 compose 命令。
- 镜像：`deploy/Dockerfile` 多阶段构建（`rust:1.91-bookworm` → `gcr.io/distroless/cc-debian12:nonroot`），以 `nonroot` 运行。推送 `v*` tag 时 CI 构建镜像，推送到 `ghcr.io/<仓库>/server:<tag>`，并用 cosign 无密钥签名。
- 服务端监听 `8787`（`bind` 默认 `0.0.0.0:8787`），compose 中只 `expose` 不映射端口，只经 Caddy 暴露。Caddy 自动申请/续期证书，TLS 版本沿用 Caddy 默认（最低 TLS 1.2），`Caddyfile` 未额外配置。
- 反向代理之后必须设 `trust_proxy = true`（compose 已设 `VAULTONE_TRUST_PROXY=true`，`Caddyfile` 以 `{remote_host}` 覆盖 `X-Forwarded-For`），限流与审计 IP 才会按真实客户端 IP 计算。直连公网时保持 `false`（否则 `X-Forwarded-For` 可伪造）。

## 2. 配置

分层加载：默认值 → `vaultone.toml`（或 `$VAULTONE_CONFIG`）→ 环境变量 `VAULTONE_*`（嵌套键用 `__`，如 `VAULTONE_MAIL__MODE`）。完整示例见 `deploy/vaultone.example.toml`。

| 键 | 默认 | 说明 |
|---|---|---|
| `server_secret` | **无** | 64 位十六进制（32 字节），缺失、非法十六进制或全部字节相同即拒绝启动（§4） |
| `bind` | `0.0.0.0:8787` | 监听地址 |
| `database_url` | `sqlite://vaultone.db?mode=rwc` | 生产用 `postgres://` |
| `session_ttl_days` | 60 | 会话滑动续期，允许 1–365 |
| `trust_proxy` | `false` | 反向代理之后置 `true`（§1） |
| `auth_rate_ms` / `auth_burst` | 3000 / 10 | 认证类接口（注册、登录、设备验证、恢复）每 IP 限流 |
| `api_rate_ms` / `api_burst` | 100 / 120 | 其他业务接口每 IP 限流（`/healthz`、`/readyz` 不限流） |
| `log_format` / `log_level` | `pretty` / `info` | 生产用 `json`；`VAULTONE_LOG`（EnvFilter 语法）优先于 `log_level` |
| `cors_origins` | 空 | 逗号分隔的允许来源；为空表示不开放 CORS |
| `version_retention_days` | 30 | 条目历史版本保留期（后台每 60 秒清理一次） |
| `mail.mode` | `log` | 只能是 `smtp` 或 `log`；生产必须为 `smtp`（且 `mail.smtp_host` 必填），否则通知邮件只写日志 |

上线前运行 `vault-server check`（容器内为 `docker compose -f deploy/docker-compose.yml --env-file deploy/.env run --rm server check`）：只校验配置、连接数据库并执行迁移，然后退出。

## 3. 健康检查与监控

| 端点 | 含义 |
|---|---|
| `GET /healthz` | 进程存活，返回版本号 |
| `GET /readyz` | 数据库可用（`SELECT 1`），不可用时返回 503 |

建议告警：`/readyz` 连续失败；5xx 比例；429 激增（可能遭遇撞库）；SMTP 发送失败日志（`target=mail`）。

## 4. 服务端主密钥（server_secret）管理

`server_secret` 派生邮箱索引、邮箱加密、SRP 握手封装、验证码 HMAC 等全部服务端密钥（docs/03 §8）。

- **只通过环境变量或密钥管理服务注入**（Vault / AWS Secrets Manager / 云厂商 KMS 等），不写入配置文件、镜像或版本库。
- **不可轮换**：更换后已有账户的邮箱索引与邮箱密文全部失效，用户将无法登录。因此必须长期保管，并至少在两处独立离线位置备份。
- 泄露影响：攻击者可解密数据库中的邮箱并伪造验证码 HMAC，但**仍无法解密任何保险库数据**（零知识，服务端没有 Vault Key 材料）。泄露后应通知用户并启动迁移流程。

## 5. 备份与恢复

- 数据库：PostgreSQL 每日 `pg_dump` + WAL 归档，异地保存，至少保留 30 天；每季度做一次恢复演练。
- 备份中只有密文、SRP verifier 与非敏感元数据，但仍视为敏感数据加密存放（泄露会暴露账户数量与元数据）。
- 恢复顺序：恢复数据库 → 以**同一个** `server_secret` 运行 `vault-server check` → 启动服务 → 确认 `/readyz` 返回 200。

## 6. 升级

- 迁移随启动自动执行（`migrations/{sqlite,postgres}`），只做向前兼容的变更；升级前先备份。
- 客户端与服务端协议以 `vault-proto` 为准，破坏性变更需提升路由版本（`/v2/...`）并保留旧路由至少一个客户端发布周期。

## 7. 安全事件响应

1. 确认影响范围（审计表、访问日志、`x-request-id`）；
2. 如涉及账户凭据：撤销相关会话（`sessions.revoked_at`；用户也可在客户端「设备管理」撤销设备，其会话随之失效），通知受影响用户修改主密码；
3. 24 小时内向受影响用户发出通知（计划书 D-05），说明零知识边界内哪些数据可能暴露（邮箱、元数据），哪些不可能（保险库内容、主密码）。
