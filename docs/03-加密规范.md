# 03 · 加密规范

> 本文是 VaultOne 全部密码学决策的**唯一规范**，第三方可据此独立实现解密（§2.4 给出已验证的固定向量）。
> 文档与代码冲突时以代码为准；每节标注实现位置。算法原语全部来自 RustCrypto，本仓库**不实现任何密码学算法**，只定义格式与组合规则（见 docs/01 §3.3）。

## 0. 交付要求对照（发布门禁）

| 要求 | 实现 | 自动化验证 |
|---|---|---|
| 所有敏感数据统一 AES-256-GCM | 唯一对称加密入口 `vault_crypto::sealed`；依赖图中 AES 只经 `aes-gcm` 使用 | `deny.toml` `[bans].deny` 禁止 `cbc`/`ecb`/`block-modes`/`cfb-mode`/`ofb`/`des`/`rc4`，任何依赖引入即 CI 失败 |

## 2. 密封盒（Sealed Box）格式 —— `crates/vault-crypto/src/sealed.rs`

### 2.1 字节布局

```text
偏移   长度  字段
0      1     version = 0x01
1      1     suite   = 0x01   (AES-256-GCM + HKDF-SHA256)
2      32    salt    每次加密由 OsRng 生成
34     12    iv      每次加密由 OsRng 生成
46     n     ciphertext
46+n   16    GCM 认证标签
```

固定开销 `OVERHEAD = 62` 字节。封装一把 256-bit 密钥的密封盒恒为 94 字节（服务端据此做结构校验，见 §7.3）。

### 2.2 加密

```text
输入：长期密钥 K（32 B）、明文 P、调用方上下文 aad
1. salt ← OsRng(32)，iv ← OsRng(12)
2. header ← 0x01 ‖ 0x01 ‖ salt ‖ iv
3. K_msg ← HKDF-SHA256(salt = salt, ikm = K, info = "vaultone/v1/sealed", L = 32)
4. A ← header ‖ u64_be(len(aad)) ‖ aad
5. C ‖ T ← AES-256-GCM-Encrypt(K_msg, iv, P, A)
输出：header ‖ C ‖ T
```

- **头部进入 AAD**：盐、IV、版本、套件任何一位被篡改，标签校验都会失败。
- **aad 带长度前缀**：防止 `header‖aad` 的拼接边界被挪动伪造（`aad_length_prefix_prevents_ambiguity`）。
- **一次性子密钥**：每条消息的实际加密密钥由随机盐派生，同一长期密钥加密海量数据也不存在 96-bit 随机 IV 的生日界（2^32 条消息）问题。

### 2.3 解密

依次检查：长度 ≥ 62 → version == 0x01 → suite == 0x01 → 按 §2.2 第 3、4 步重算 `K_msg` 与 `A` → GCM 解密并校验标签。除「未知版本/套件」外，一切失败（密钥错、aad 不符、篡改、截断）统一返回 `Integrity`，不给攻击者区分信号。

### 2.4 固定向量（第三方互操作）

| 项 | 值 |
|---|---|
| K | 32 字节 `0x42` |
| aad | ASCII `vaultone/doc-vector` |
| 明文 | ASCII `VaultOne interop vector`（23 B） |
| 密封盒（85 B，hex） | `01014f404cc75de75ce8328cc1e76376b11224ec0b013f6b03d8781eada21fe81287c5eb701b05a15a6769a987b536ea09a9ee316ee9adfd705c406758465b86b31079e6c1425a0ad7ad7bb37c38c67ec7b492b0f7` |

参考实现（只依赖 Python `cryptography`，已对上表向量验证通过；错误 aad 抛 `InvalidTag`）：

```python
import struct
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

def open_sealed(key: bytes, sealed: bytes, aad: bytes) -> bytes:
    assert sealed[0] == 0x01 and sealed[1] == 0x01, "version/suite"
    header, body = sealed[:46], sealed[46:]
    salt, iv = header[2:34], header[34:46]
    k_msg = HKDF(algorithm=hashes.SHA256(), length=32, salt=salt, info=b"vaultone/v1/sealed").derive(key)
    return AESGCM(k_msg).decrypt(iv, body, header + struct.pack(">Q", len(aad)) + aad)
```

同一向量固化为 Rust 单测 `sealed::tests::fixed_vector_from_spec`，格式一旦变化即失败。

## 3. 密钥层级 —— `vault-crypto/src/kdf.rs`、`vault-core/src/vault.rs`、`envelope.rs`

```text
主密码 ──NFKD──┐
               ├─ Argon2id(salt_kdf) ─┐
Secret Key ────┴─ HKDF ───────────────┴─ XOR ─> MUK
MUK ──HKDF──> AuthKey ──> SRP-6a verifier（上传服务端）
MUK ──HKDF──> WrapKey ──密封盒──> Vault Key（随机 256-bit，注册时生成，终身不变）
Recovery Code ──HKDF──> RecoveryWrapKey ──密封盒──> Vault Key
Recovery Code ──HKDF──> RecoveryAuthToken ──SHA-256──> 服务端（证明持有恢复码）
快速解锁密钥 QK（随机 256-bit，存系统钥匙串）──密封盒──> Vault Key
Vault Key ──密封盒──> Item Key（每条目、每次写入重新随机）──密封盒──> 条目 JSON
Vault Key ──密封盒──> 邮箱、同步会话 token（本地库）
```

### 3.1 派生标签（HKDF info，均为 UTF-8）

| 派生物 | ikm | salt | info |
|---|---|---|---|
| Secret Key 分量 | Secret Key（30 B） | salt_kdf | `vaultone/v1/secret-key\|<account_id>` |
| AuthKey | MUK | salt_kdf | `vaultone/v1/auth\|<account_id>` |
| WrapKey | MUK | salt_kdf | `vaultone/v1/wrap\|<account_id>` |
| RecoveryWrapKey | Recovery Code（32 B） | 无 | `vaultone/v1/recovery-wrap\|<account_id>` |
| RecoveryAuthToken | Recovery Code | 无 | `vaultone/v1/recovery-auth\|<account_id>` |
| 密封盒消息密钥 | 长期密钥 | 每次随机 32 B | `vaultone/v1/sealed` |

`account_id` 参与每一次派生：同一口令在不同账户下得到互不相关的密钥。Recovery Code 自身有 256-bit 熵，因此不需要内存硬 KDF；它作为密封盒长期密钥时，密封盒内部仍会以每次随机的 32 B 盐做 HKDF。

### 3.2 各密封盒的 aad（上下文绑定）

aad 不随密文存储，由读取方按「这份密文应该在哪里」重新计算——密文被挪到别处即解密失败。

| 密文 | 加密密钥 | aad |
|---|---|---|
| Vault Key 封装 `vk_wrap` | WrapKey | `vaultone/vault-key\|<account_id>` |
| 恢复封装 `recovery_wrap` | RecoveryWrapKey | `vaultone/recovery\|<account_id>` |
| 快速解锁封装 | QK | `vaultone/quick-unlock\|<account_id>` |
| 邮箱（本地） | Vault Key | `vaultone/email\|<account_id>` |
| 同步会话 token（本地） | Vault Key | `vaultone/session-token\|<account_id>` |
| 本机保密设置（浏览器扩展配对密钥等） | Vault Key | `vaultone/setting/<key>\|<account_id>` |
| Item Key | Vault Key | `vaultone/item-key\|<item_id>\|<vault_id>` |
| 条目内容 | Item Key | `vaultone/item\|<item_id>\|<vault_id>\|<revision>` |
| 本机冲突工作记录 | Vault Key | `vaultone/conflict/v1\|<account_id>\|<vault_id>\|<item_id>\|<conflict_id>` |
| 服务端：邮箱 | 服务端 email-enc 子密钥 | `vaultone-server/email` |
| 服务端：SRP 临时私钥 b | 服务端 handshake 子密钥 | `<handshake_id>` |

## 4. 主密码派生（2SKD）—— `crates/vault-crypto/src/kdf.rs`

```text
salt_kdf = OsRng(32)                         注册、改密、恢复时都换新盐
A        = Argon2id(NFKD(主密码), salt_kdf, m=65536 KiB, t=3, p=4, len=32)
S        = HKDF-SHA256(ikm=SecretKey, salt=salt_kdf, info="vaultone/v1/secret-key|<account_id>")
MUK      = A XOR S
```

- **双因子**：即使服务端的盐与 KDF 参数被拖库，攻击者没有设备上的 240-bit Secret Key 也无法离线爆破主密码（计划书 S-02）。两路独立派生再异或，任一路都不单独决定结果。
- **NFKD 规范化**：不同输入法/系统输入的同一口令（如预组合 `é` 与 `e`+组合符）得到同一密钥（`nfkd_normalizes_equivalent_input`）。
- **防降级**：客户端拒绝 `m < 19 MiB`、`t < 2`、盐 < 16 B 或非 argon2id 的参数（OWASP 2024 下限），服务端注册/改密接口做同样校验——被篡改的库或服务端无法诱导客户端用弱参数派生。仅测试构建（`insecure-test-kdf` 特性 + 服务端 `allow_test_kdf`）放行 `m=8,t=1,p=1` 这一组固定低成本参数。
- **主密码长度**：≥ 10 个字符；UI 同时用 zxcvbn 给出强度反馈。

### 4.1 Secret Key 与 Recovery Code 编码 —— `crates/vault-crypto/src/keys.rs`

| | 熵 | 格式 | 保存位置 |
|---|---|---|---|
| Secret Key | 240 bit（30 B） | `V1-XXXXXX-…`（8 组 × 6 位 Crockford Base32） | 本机系统安全存储 + Recovery Kit |
| Recovery Code | 256 bit（32 B） | `R1-XXXX-…`（13 组 × 4 位 Crockford Base32） | **仅** Recovery Kit |

Crockford Base32 不含 I/L/O/U；解析时忽略空白与 `-`，大小写不敏感，并把手抄易混的 `I/L→1`、`O→0` 自动纠正。

## 5. 条目信封 —— `crates/vault-core/src/envelope.rs`

写入 `items.blob` 并原样同步到服务端：

```json
{"v":2,"alg":"aes-256-gcm","wrappedKey":"<密封盒 b64>","ct":"<密封盒 b64>"}
```

1. 每次写入（新建、编辑、删除、恢复、合并）都生成**新的随机 Item Key**，`wrappedKey = seal(VaultKey, ItemKey, aad=item-key|item|vault)`；
2. 条目 JSON 按 ISO/IEC 7816-4 填充（`0x80` 后补零）到 **256 字节整数倍**，缓解长度泄露（计划书 §3.1）；
3. `ct = seal(ItemKey, 填充后明文, aad=item|item|vault|revision)`。

**版本号绑定 aad** 的效果：服务端或网络中间人把旧版本密文回放给客户端（版本回滚），或把 A 条目密文挪给 B 条目，都会校验失败（`rejects_replay_to_other_item_vault_or_revision`）。单条校验失败只跳过该条目并记录错误日志，不影响其余保险库（`tampered_or_replayed_blob_is_skipped_not_fatal`）。

## 6. 本地存储 —— `crates/vault-core/src/store.rs`

本地 SQLite（`rusqlite` bundled）是唯一真相源。**采用「应用层逐字段加密」而非 SQLCipher 整库加密**：

| 表 / 字段 | 内容 | 是否加密 |
|---|---|---|
| `meta.account` | account_id、vault_id、KDF 参数与盐、`vk_wrap`、`recovery_wrap`、SRP 盐与 verifier、`email_enc` | 密钥材料均为密封盒；KDF 参数与盐按设计公开 |
| `meta.remote` | 服务器地址、设备 ID/名、`token_enc` | token 为密封盒 |
| `meta.quick_unlock` | `seal(QK, VaultKey)` | 密封盒 |
| `items` | id、vault_id、**kind**、blob、revision、时间戳、同步标记、基线墓碑状态 | blob 为条目信封；kind/时间戳为非敏感元数据 |
| `item_conflicts`（本地 schema v2） | id、vault_id、item_id、状态及 blob | blob 使用 Vault Key 密封，保存基线/双方原信封、原版本和裁决结果；字段名与内容不放明文列。标识和状态仍是可见元数据 |
| `settings` | 自动锁定时长、切后台/最小化时锁定、剪贴板秒数、主题、服务器地址、详细日志开关、隐私同意版本、桌面托盘 / 全局快捷键 / 浏览器集成开关 | 非敏感偏好，明文 |
| `settings` 中 `sealed:*` 键 | 浏览器扩展配对密钥（`sealed:browser_clients`） | 密封盒（§3.2），锁定时不可读 |

为什么不用 SQLCipher：

1. **收益有限**：SQLCipher 保护的是「文件被拿走」的场景，而本方案下文件中本来就只有密封盒——`database_file_has_no_plaintext` 在真实磁盘文件（含 WAL）中检索邮箱、标题、URL、用户名、密码、TOTP 密钥均 0 命中；
2. **成本高**：SQLCipher 依赖 OpenSSL/CommonCrypto，需要在 Windows/macOS/iOS/Android 四端交叉编译与维护，扩大供应链面（计划书 R-05）；
3. **密钥时机**：整库加密要求在读取任何数据前就持有密钥，而锁定态也需要读取 KDF 参数、判断是否已初始化；
4. **不建明文索引**：搜索在解锁后于内存中完成（`items` 无明文列），避免计划书 §4.2 `index_ft` 那样把解密后的索引落盘。

其他措施：`PRAGMA secure_delete=ON`（删除/更新的旧页被覆写，不残留在空闲页）；Android `allowBackup=false` + `dataExtractionRules` 排除全部域，iOS/macOS 钥匙串项使用 `*_this_device` 可访问性，均不随备份迁移。

**元数据可见性（如实说明）**：本地库与服务端都能看到条目数量、类型（登录/卡片/笔记/身份）、版本号、时间戳与填充后的长度区间；看不到标题、URL、用户名、密码、备注、TOTP 等任何字段。

## 7. 认证与传输

### 7.1 SRP-6a —— `crates/vault-crypto/src/srp6a.rs`

- 口令 = AuthKey（256-bit，由主密码 + Secret Key 派生）；身份 `I` = account_id（UUID，不含邮箱）；服务端只存 `(srp_salt, verifier)`。verifier 由 256-bit 密钥计算，**不存在可离线爆破的口令哈希**（计划书 S-01）。
- **双向认证**：当前 `srp 0.6.0` 线协议使用最短无符号大端整数编码，`M1 = H(BE(A)‖BE(B)‖BE(S))`、`M2 = H(BE(A)‖M1‖BE(S))`，其中 `S` 是共享整数，不是 `H(S)`；`u` 的 A/B 也不定长补齐。客户端校验 M2（`fake_server_rejected`）；恶意的零公钥被拒绝（`malicious_zero_public_rejected`）。Java 迁移须与 [S0 固定向量](10-服务端迁移契约基线.md#6-srp-字节级契约不得猜算法) 逐字节对齐，不能采用另一 SRP 库的默认证明格式。
- 服务端握手状态（临时私钥 b）用服务端密钥封装后存库、120 秒过期、一次性（先删后验，防重放），因此支持多实例水平扩展。
- **防账户枚举**：未注册邮箱返回由 HMAC 确定性生成的伪造 account_id / KDF 盐 / SRP 盐 / verifier，响应形态与真实账户一致；错误密码与不存在的账户返回同一错误。

### 7.2 会话与传输

- 会话 token：32 B `OsRng` → base64url；服务端只存 SHA-256；滑动续期（默认 60 天）；撤销设备即撤销其全部会话；恢复账户会撤销所有既有会话。
- 客户端只允许 `https://` 同步地址（回环地址 `localhost/127.0.0.1/[::1]/10.0.2.2` 例外，供本地开发）；reqwest 使用 rustls，不依赖系统 OpenSSL；Android `usesCleartextTraffic=false`。
- 服务端响应头：`Strict-Transport-Security`、`Cache-Control: no-store`、`X-Content-Type-Options`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`；生产部署经 Caddy 自动申请证书，仅 TLS 1.2+。
- 证书固定（计划书 §3.1 提及）当前**未实现**：同步地址允许用户自建服务器，固定证书会与之冲突；零知识设计下即使 TLS 被中间人攻破，攻击者也只能看到密文与 SRP 交换（SRP 本身不泄露可爆破信息）。

### 7.3 服务端零知识门禁 —— `crates/vault-server/src/validate.rs`

服务端虽然看不懂密文，但校验其**结构**：`vk_wrap`/`recovery_wrap` 必须是 94 字节、版本/套件正确的密封盒；条目 blob 必须是恰好 4 个字段的 v2 信封，`wrappedKey` 为合法密封盒，`ct` 的密文体长度为 256 的非零整数倍。客户端（包括被篡改的客户端）因此无法把明文当作 blob 上传（`accepts_real_envelopes_only`）。

## 8. 服务端密钥 —— `crates/vault-server/src/keys.rs`

全部由 `server_secret`（32 B，`vault-server gen-secret` 生成，经环境变量或密钥管理服务注入）派生，不落盘、不硬编码：

```text
K_label = HKDF-SHA256(ikm = server_secret, salt = "vaultone-server/v1", info = label)
```

| label | 用途 |
|---|---|
| `email-index` | `HMAC(规范化邮箱)` → 登录查找索引（不可反查） |
| `email-enc` | 密封盒加密邮箱（仅用于发送通知邮件时解密） |
| `handshake` | 密封盒加密 SRP 临时私钥 b |
| `decoy` | 未注册邮箱的伪造参数；客户端 IP 的 16 字节 HMAC（审计用，不可反查） |
| `otp` | `HMAC(user‖device‖验证码)`：新设备 6 位验证码只存 HMAC，10 分钟有效、最多 5 次尝试 |

`server_secret` 校验：必须 64 位十六进制（32 B）且不能全为同一字节，否则拒绝启动。**轮换 `server_secret` 会使已有邮箱索引与邮箱密文失效**，生产环境须通过密钥管理服务长期保管（docs/05 §4）。

## 9. 恢复（Recovery Kit）

1. 注册时生成 Recovery Code，只出现在 Recovery Kit（PDF，本机生成，不经网络）；本地与服务端只保存 `recovery_wrap` 与 `SHA-256(RecoveryAuthToken)`；
2. 忘记主密码（本机）：恢复码 + Secret Key → 解封 Vault Key → 设新主密码（换新 KDF 盐）→ **生成新恢复码**，旧恢复码立即作废；
3. 所有设备丢失（云端）：`/v1/recovery/fetch` 用 RecoveryAuthToken 证明持有恢复码（服务端常量时间比较哈希）→ 取回 `recovery_wrap` 本地解封 → `/v1/recovery/complete` 上传新凭据并轮换恢复码，服务端撤销全部旧会话并邮件告警；
4. 零知识边界：服务端没有任何能解开 Vault Key 的材料，**无法替用户重置主密码或找回数据**（计划书 §7.2 合规红线）。

## 10. 快速解锁（生物识别）

启用时生成随机 256-bit QK：QK 写入系统安全存储（iOS/macOS 钥匙串 `first_unlock_this_device`、Android 由 Keystore 保护的密钥加密、Windows DPAPI 加密文件，均绑定本机与当前用户），本地库只存 `seal(QK, VaultKey)`，**两者缺一不可**（`quick_unlock_requires_both_halves`）。主密码变更、恢复、或其他设备改密后同步到本机时，快速解锁材料一律作废，必须重新用主密码解锁。

## 10.1 浏览器扩展通道 —— `crates/vault-core/src/browser.rs`

扩展（MV3）→ Native Messaging 宿主 `vaultone-nmhost`（只转发）→ 本地套接字 → 桌面端。解密只在桌面端进程内发生。

| 环节 | 规则 |
|---|---|
| 本地套接字 | Windows：按用户名区分的命名管道，拒绝远程客户端；macOS / Linux：权限 0600 的 Unix 域套接字（macOS 位于 App Group 容器） |
| 配对 | 扩展以 WebCrypto CSPRNG 生成 256-bit 配对密钥发给桌面端；桌面端弹窗显示 `SHA-256(密钥)` 前 40 bit 的 Crockford Base32（`XXXX-XXXX`），用户核对与扩展弹窗一致后批准。仅在解锁状态下可配对 |
| 请求认证 | `HMAC-SHA256(配对密钥, "vaultone-browser/v1⏎" ‖ clientId ‖ "⏎" ‖ nonce ‖ "⏎" ‖ ts ‖ "⏎" ‖ body)`（⏎ 为换行符 0x0A），常量时间校验；`ts` 与本机时间相差不超过 120 s；nonce（≥ 16 字符）在最近 4096 条内不得重复 |
| 凭据释放 | `fill` / `totp` 必须携带页面地址且通过 URL 匹配（`urlmatch.rs`，eTLD+1 / 协议降级拒绝）；地址由扩展后台取自浏览器提供的 `sender.url`，不采信页面脚本自报 |
| 保存 | 扩展提交的网址只保留协议 + 主机 + 端口（去掉路径与查询参数中的会话信息） |
| 锁定态 | 配对密钥为密封盒，锁定时无法校验，任何请求只返回 `locked` |

威胁模型边界：同一用户身份下运行的恶意程序可读取扩展的 `chrome.storage.local` 取得配对密钥，但仍只能在桌面端**已解锁**时按页面地址逐条请求；对此类本机恶意代码，密码管理器普遍无法完全防御（同 §12 生物识别一行）。

## 10.2 Android 自动填充 —— `app/android/.../autofill/`

`AutofillService` 只解析表单结构，返回需要认证的响应，本身不接触凭据；用户点选后由 `AutofillActivity`（Flutter，必要时先解锁）让用户选择条目，再把用户名 / 密码作为数据集交给系统。网页表单按系统提供的 `webDomain` 经 `urlmatch` 推荐匹配项；应用内表单不做自动匹配，由用户搜索选择。自动填充界面与主界面同进程共用同一个保险库实例，锁定状态共享。

## 10.3 条目级加密备份与 CSV —— `crates/vault-core/src/export.rs`

`.wljbak` 当前格式为 `WLJBAK` 六个 ASCII 字节、版本字节 `0x01`，随后是 §2 密封盒。密封盒使用原账户 Vault Key，调用方 AAD 为原 `account_id` 的 UTF-8 字节。载荷是 `{"format":1,"exportedAt":<Unix秒>,"items":[<ItemData>...]}`，随机盐、IV 与认证标签均由既有密封盒实现提供；迁移服务端不改变该格式。

- 这是**条目级恢复，不是数据库快照回滚**：只包含未删除条目的完整 `ItemData`（含卡片/身份字段、自定义字段、全部 URL、历史与 TOTP 配置），不包含回收站、账户密钥封装、会话、设备配对或偏好。
- 导入会生成新的条目 ID、revision 与创建/更新时间，不覆盖已有条目。备份内部仍携带原条目的时间字段，但它们不用于恢复原数据库身份。
- 灾难恢复必须先恢复**同一账户及其原 Vault Key**，再导入文件。主密码 + Secret Key 本身不能从此文件推导 Vault Key；还需要保留的账户密钥封装，或可用的云端账户恢复材料。仅有 `.wljbak` 文件、或使用相同邮箱新注册账户，均不能恢复。恢复套件应与备份分开妥善保存。
- 当前格式不代表兼容旧 passmgr 的同名扩展名；版本未知、账户/密钥不匹配、截断或认证失败必须拒绝。
- 本机冲突工作记录不在 v1 条目备份范围，也不上传云端。存在 `pending` / `resolution_pending` 时导出明确拒绝，须先裁决并取得同步确认，避免静默遗漏另一方候选；已解决/被替代的工作历史仅留在本地库，备份恢复不重建该历史。本地库升级与旧客户端降级须分别验收。
- CSV 为**明文、有损迁移格式**，列固定为 `name,url,username,password,notes,totp,favorite,type`。只输出首个 URL 和 TOTP 种子，不保留匹配策略、其他 URL、完整 TOTP 参数、自定义字段、卡片/身份专用字段或密码历史，不应作为完整备份。将不可信 CSV 交给电子表格软件还可能触发公式解释，推荐仅通过目标密码管理器导入。
- 文件生成不等于成功落盘，也不等于用户已经确认恢复材料。UI 应在实际写入完成后报告路径与大小，写入失败时提示清理可能残留的不完整文件（CSV 残留仍为明文）。

## 11. 内存与运行时

- `Key32`：`memsec::malloc` 独立分配，页面 `mlock/VirtualLock` 防写入 swap，前后保护页防越界，释放前清零；`Debug` 输出为 `Key32(<redacted>)`；比较为常量时间。
- 口令、Secret Key、恢复码、解密后的明文缓冲区在 Rust 侧均为 `Zeroizing`，离开作用域即清零。
- 锁定：Vault Key 只存在于内存会话中，锁定时即丢弃。触发方式有手动锁定、空闲超时（默认 10 分钟）和最小化/切后台（可选，移动端默认开启）。锁定同时清空由本应用写入的剪贴板内容。
- 剪贴板：桌面端（Windows / macOS / Linux）经 Rust `arboard` 写入。Windows 下标记「不进入剪贴板历史 / 不云同步 / 不被监控」，macOS / Linux 下标记 `exclude_from_history`。到期（默认 30 秒）后仅当内容仍是本应用写入的那一份时才清空，比较 SHA-256，不在内存保留明文。移动端使用系统剪贴板，清除前需与内存中暂存的复制文本比对，因此到期或锁定前该文本会留在 Dart 内存中。
- 日志：绝不记录主密码、Secret Key、条目内容、邮箱明文、会话 token；客户端 panic 只记录源码位置（服务端 panic 的处理差异见 docs/04 §3）。

## 12. 已知局限（诚实披露）

| 局限 | 影响 | 计划 |
|---|---|---|
| 生物识别只在应用层把关：QK 所在的钥匙串/Keystore 项未绑定生物识别访问控制 | 能以本应用身份读取系统安全存储的恶意代码（已越狱/root 设备）可绕过生物识别，但仍需本地库中的密封盒 | 改用 iOS/macOS `biometryCurrentSet` 访问控制与 Android BiometricPrompt 绑定密钥 |
| Dart 字符串不可清零：条目明文经 FFI 以 JSON 进入 Dart 后由 GC 管理 | 进程内存 dump 可能在 GC 前残留明文（计划书 B-04 需内存取证验证） | 缩短明文在 Dart 侧的驻留（按需解密单条、列表只传摘要字段） |
| 元数据可见（§6 末） | 服务端可推断条目数量与类型分布、活跃时间 | 可选：条目类型并入密文、批量填充条目数 |
| 其他设备改密后，本机接受新的 `vk_wrap` 时只校验结构 | 恶意服务端可推送无法解开的封装，造成拒绝服务（不泄露数据） | 以 Vault Key 对封装数据加 MAC，客户端校验 |
| 撤销设备不轮换 Vault Key | 被撤销的设备本地仍保有 Vault Key 与撤销前已同步的数据；撤销只阻止它继续从服务端取得新数据 | V1.1 提供「轮换保险库密钥」（重新封装全部 Item Key） |
| 暂无国密套件（SM4-GCM / SM3 / SM2） | 不满足国内政企采购（计划书 P2） | 密封盒 `suite` 字节已预留：新增 `0x02` 即可并行支持 |

## 13. 格式演进

- 密封盒以 `version`/`suite` 字节演进：新增算法只需分配新的 suite 值，读取方按字节分派，旧数据继续可读；未知版本/套件返回 `Unsupported` 而非 `Integrity`，便于诊断。
- 条目信封以 `v` 字段演进（当前 v2）；服务端只接受当前版本，防止降级到旧格式。
- 本地 SQLite schema v2 新增冲突工作表与基线墓碑字段。升级在事务中完成，新实现拒绝高于自身支持版本的库；**旧版客户端原实现没有未来版本拒绝逻辑，不得让旧二进制直接打开升级后的同一库文件**。本轮不承诺本机数据库降级，回退应使用升级前独立备份并另行核对升级后的新增数据，不能直接覆盖丢弃新写入。
- KDF 参数随账户存储：提高 Argon2id 成本只需在下次改密时写入新参数，不影响已有数据。
