## 2. HTTP 清单

认证记号：公开 = 不要求会话；会话 = `Authed`，允许未批准设备；批准 = `Approved`。会话与批准路由统一可能返回 `401 unauthorized`，批准路由另有 `403 device_not_approved`；所有路由可能遇到内部故障，认证/API 两组还有限流。表中列出主要业务分支，框架拒绝另见后文。

| 方法 / 路径 | 权限 | 请求 | 成功状态 / 响应 | 主要业务错误 |
|---|---|---|---|---|
| POST `/v1/auth/register` | 公开 | RegisterRequest | **201** LoginFinishResponse；m2 为 `""`，首台设备已批准，keys 非 null | 400 校验；409 email_taken |
| POST `/v1/auth/login/start` | 公开 | LoginStartRequest | 200 LoginStartResponse；不存在邮箱仍返回伪装参数 | 400 邮箱 |

这是 18 个 `/v1` 方法/路径组合，加 2 个健康接口；不要照旧文档“19 个路由”直接计数。

### 错误与框架行为

业务错误形态为 `{"code":string,"message":string}`。稳定码全集及当前映射：

- `bad_request` → 400；`unauthorized` → 401；`auth_failed` → 401（撤销设备登录例外为 403）。
- `device_not_approved` → 403；`conflict`、`email_taken` → 409；`not_found` → 404。
- `rate_limited` → 429；`internal` → 500。DB、anyhow、内部 serde 错误细节不回传。
- 未知路径 404 JSON `not_found`；已知路径不支持的方法走 Axum 405，而非业务 ErrorBody。
- **并非所有错误都为 JSON**：未自定义 Axum `Json`/`Query` rejection。无 JSON Content-Type → 415；坏 JSON 语法 → 400；缺字段/类型不匹配 → 422；这些 Json 拒绝为 `text/plain`。体积拒绝为 413。不能把源文件“所有错误 JSON”的注释当成事实。
- message 用于展示，不宜作为客户端分支条件；Java 兼容测试应分别断言业务与框架拒绝，不能用默认 Spring ProblemDetail 替换而不评估客户端。

中间件：默认 body 上限 1 MiB；push 路由单独 64 MiB。认证组（register、login start/finish、self verify、recovery 三项）按 IP 默认 3000 ms 补充一次、burst 10；其他 `/v1` 组 100 ms、burst 120。健康接口不在这两组内。`trust_proxy=false` 取真实 ConnectInfo；true 使用代理提取器。限流数据当前是进程内，并非 Redis。

响应头设 `Cache-Control:no-store`、`X-Content-Type-Options:nosniff`、`X-Frame-Options:DENY`、`Referrer-Policy:no-referrer`、`Strict-Transport-Security:max-age=63072000; includeSubDomains`；设置/传播 `x-request-id`。CORS 为配置中的显式来源，允许 GET/POST/PUT/DELETE 和 Authorization/Content-Type，默认不开放来源。

## 3. DTO 与序列化清单

以下 `s`=字符串，`i`=有符号 64 位 JSON 整数，`u32`=无符号 32 位 JSON 整数，`b`=JSON 布尔，`B`=`Bytes`，`?`=可为空的 Option，`[]`=数组。字段名严格保留 snake_case（只有密封条目信封的 wrappedKey 是 camelCase）。不是 Java 的默认 camelCase。

| DTO | 字段（完整） |
|---|---|
| ErrorBody | code:s, message:s |
| KdfParams | alg:s, m:u32, t:u32, p:u32, salt:s |
| DeviceInfo | id:s, name:s, platform:Platform |
| AccountKeys | account_id:s, vault_id:s, kdf:KdfParams, vk_wrap:B, vk_gen:i, recovery_wrap:B |
| SessionInfo | token:s, expires_at:i, device_id:s, device_approved:b |
| RegisterRequest | email:s, keys:AccountKeys, srp_salt:B, srp_verifier:B, recovery_auth_hash:B, device:DeviceInfo |
| LoginStartRequest | email:s |
| LoginStartResponse | handshake_id:s, account_id:s, kdf:KdfParams, srp_salt:B, b_pub:B |
| LoginFinishRequest | handshake_id:s, a_pub:B, m1:B, device:DeviceInfo |
| LoginFinishResponse | m2:B, session:SessionInfo, keys:AccountKeys? |
| VerifyDeviceRequest | code:s |
| AccountResponse | email:s, keys:AccountKeys |
| ChangeCredentialsRequest | kdf:KdfParams, srp_salt:B, srp_verifier:B, vk_wrap:B, expected_vk_gen:i, recovery_wrap:B?, recovery_auth_hash:B? |
| ChangeCredentialsResponse | vk_gen:i |
| RecoveryStartRequest | email:s |
| RecoveryStartResponse | account_id:s |
| RecoveryFetchRequest | email:s, recovery_auth:B |
| RecoveryCompleteRequest | email:s, recovery_auth:B, kdf:KdfParams, srp_salt:B, srp_verifier:B, vk_wrap:B, recovery_wrap:B, recovery_auth_hash:B, device:DeviceInfo |
| RecoveryCompleteResponse | session:SessionInfo, keys:AccountKeys |
| DeviceOut | id:s, name:s, platform:Platform, approved:b, current:b, created_at:i, last_seen_at:i?, revoked_at:i? |
| AuditEventOut | event:s, device_id:s?, created_at:i |
| PushItem | id:s, kind:s, blob:B, base_revision:i, revision:i, deleted:b, updated_at:i |
| PushRequest | items:PushItem[] |
| PushResult | id:s, status:PushStatus, revision:i |
| PushResponse | results:PushResult[] |
| RemoteItem | id:s, kind:s, blob:B, revision:i, deleted:b, updated_at:i |
| PullResponse | items:RemoteItem[], cursor:i, has_more:b, vk_gen:i? |

- `Bytes` 是 RFC 4648 **STANDARD** Base64（`+/`、需要相应 `=` padding），不是 URL-safe；空字节串为 `""`，不是 null/[]。例如 `[0,1,2,255]` → `"AAEC/w=="`。解码拒绝缺失必要 padding、URL-safe 字符、空白以及非字符串。
- `KdfParams.salt` 自身是字符串，业务校验时再按相同 STANDARD 解码；不要二次 Base64。
- Option 序列化**显式输出 null**，没有 skip_serializing_if。缺失 Option 字段也能反序列化为 None。credentials 两个恢复字段与 pull.vk_gen 明确有 serde default。其余非 Option 字段无默认：缺字段/传 null 拒绝；空数组合法。
- 普通 DTO 没有 deny_unknown_fields，未知字段被忽略；条目信封则要求恰好 4 个字段（见校验）。JSON 对象成员顺序不属于契约。
- Platform wire 枚举：`windows,macos,linux,ios,android,extension,other`；未知/大小写不同输入拒绝。DB 输出的 `Platform::parse` 是另一条路径，未知值回退 other。
- PushStatus：`applied,conflict`。kind 作为字符串另外校验。
- 时间在 HTTP 为 Unix **秒整数**，不是 ISO 字符串；当前 DB 已改 ISO-8601 TEXT，不应因此更改 wire 类型。长整数字段不能经浮点丢精度。

## 4. 校验与业务状态

- 邮箱只作现有轻量校验：trim 后 UTF-8 字节长度 ≤254、存在首个 @、本地部分非空、域部分含 `.`。不等于 RFC 完整验证或 IDNA；不能擅自套 Java 严格邮箱验证改变接受集合。
- 规范化：Rust `trim().to_lowercase()`（Unicode），无 NFKC/IDNA/点号折叠/plus 别名规则。Java 须按 Rust Unicode 行为复核，而非依赖默认 Locale/trim；本批固定邮箱是 ASCII，不声称覆盖所有 Unicode。
- 指定 account_id、vault_id、device.id、item.id 用 `Uuid::parse_str` 校验；存储仍是传入字符串，未统一 canonicalize。设备路径 id 没有显式 UUID 校验。
- 设备名 trim 后按 Unicode scalar 个数 1..64，存 trim 后名称；Java UTF-16 length 不能直接等价。
- 生产 KDF：alg=`argon2id`，m=19456..4194304 **KiB**，t=2..64，p=1..16，盐解码 ≥16B；推荐 m=65536,t=3,p=4、盐32B。仅测试允许 m=8,t=1,p=1；不得在生产开放该例外。
- SRP salt 16..64B；verifier 长度 1..384B；这里只验长度，不证明 verifier 合法。finish 的 A/M1 无额外显式长度上限（仍受 HTTP body 限制），由 SRP 校验。
- wrapped key 长度 **94B**（2B版本/套件+32B盐+12B IV+32B密文+16B tag），前两字节均1。不是旧注释隐含的93B。recovery_auth_hash 长度32B。
- blob 解码后的字节 ≤1 MiB，内容是 JSON 对象且恰好 `v,alg,wrappedKey,ct` 4键；v=2，alg=`aes-256-gcm`；wrappedKey 与 ct 是 STANDARD Base64；前者须94B盒；后者头字节01/01且 `(len-62)>0` 并为256倍数。仅结构校验，不验证 tag/明文；不能宣称服务端能够证明密文内没有明文。
- push items ≤500（空数组允许）；kind 仅 login/card/note/identity；revision≥1、revision>base_revision、base_revision≥0。未校验 updated_at 的业务时间范围。
- pull 默认 cursor=0、limit=500；cursor 负值钳至0，limit 钳至1..1000；按全局 change_log.seq 取当前用户 seq>cursor。额外取1项判 has_more，空页保留输入钳制后 cursor；返回当前 vk_gen 非 null。不是 offset 分页。
- 已存在 item：当前 revision 与请求 revision 相同且 blob SHA256 相同即 applied；否则当前 revision==base_revision 才更新；否则返回当前 revision 的 conflict。不存在 item 直接插入（不另要求 base_revision=0）。幂等依据不含 kind/deleted/updated_at。
- 同步单批事务；item_versions 按版本保留，change_log 每条目仅最新一行，不能拿 Envers revision 或 Redis 计数器直接替代现有 cursor。
- 注册存 vk_gen=max(请求,1)。credentials 实际要求 **expected_vk_gen>当前值** 并直接设为该值，与“当前代次”字段注释不同；两个可选恢复字段各自 COALESCE，不强制成对出现。迁移不得擅自改成 equality CAS。
- 本基线尚有并发弱点：login_finish SELECT 与 DELETE 分两句（顺序重放会失败，但不证明并发单次消费）；改密 UPDATE 有旧代次条件但不检查 rows_affected；push 读后更新未追加旧版本 WHERE 条件。此处仅记录，不在 S0 修复，不据此宣称线性一致或生产并发已验收。
- session：32B 随机值编码 URL_SAFE_NO_PAD 形成 token，库中 SHA256 的输入是 **token 字符串 UTF-8**，不是解码后的32B。前缀要求精确 `Bearer `，随后 trim；默认60天，expires_at<now 失效，撤销会话/设备失效；每小时至多一次滑动续期。SRP 共享值不充当 Bearer token。
- 未批准设备拿 session 但 keys=null，可 self/verify/logout，其他批准路由403。OTP 随机6位数字字符串（保留前导0），600秒、最多5次错误，比较前 trim；重复已批准 verify 直接成功。
- handshake 120秒，先查再删再校验；未知邮箱持久化 user_id=null 的 decoy handshake。decoy account_id 为16B输出经 UUID v4/variant 位设置，label=`account-id`；盐 labels=`kdf-salt`,`srp-salt` 均32B，verifier label=`verifier` 384B。
- recovery_auth 校验 SHA256(raw bytes) 与库中 recovery_auth_hash 常量时间比较；无额外输入长度检查。complete 轮换凭据/恢复封装、vk_gen+1，撤销所有既有会话，重新批准当前设备并签发新会话（不是删除所有其他设备）。

## 5. 服务端密钥、邮箱与密封盒

所有以下字符串均按 UTF-8/ASCII 原样取字节，无结尾 NUL。长度前缀以**字节数**计，不是字符数。

1. `server_secret` 配置为64位 hex（32B）；无默认值。配置校验拒绝所有字节相等的值。仅此检查不等于密码学熵评估。
2. 每个子密钥是 `HKDF-SHA256(IKM=secret, salt="vaultone-server/v1", info=label, L=32)`。
3. labels 为 `email-index,email-enc,handshake,decoy,otp`。
4. 私有 MAC 函数输入不是裸拼接：对于每一 part，先拼 `u64be(part.len)`，再拼 part；最后 HMAC-SHA256。
5. email_hash：email-index 子密钥、单 part=normalize(email) UTF-8。
6. OTP：otp 子密钥、三 parts=user_id、device_id、code；不能把 `000123` 当数字123。
7. decoy：decoy 子密钥；每块 parts=normalize(email)、label、u32be(counter)，counter从0起；逐块拼接 HMAC 输出后截至所需长度。最后 part 的长度前缀是8字节数值4，随后才是4字节计数器。
8. 邮箱长期密钥=email-enc，明文=normalize(email)，外部AAD=`vaultone-server/email`。握手长期密钥=handshake，明文=64B b，外部AAD=handshake_id 字符串。

密封盒布局：`01 | 01 | salt[32] | iv[12] | ciphertext[n] | tag[16]`；header前46B，总开销62B。消息密钥=`HKDF-SHA256(IKM=长期密钥, salt=盒内salt, info="vaultone/v1/sealed", L=32)`。AES-256-GCM 的 AAD=`header || u64be(外部AAD字节长度) || 外部AAD`；nonce=12B IV，tag=16B。生产 seal 每次独立随机盐和 IV；**黄金向量固定随机输入只允许用于测试**。错误版本/套件、错误AAD、错误key、篡改/截断均不得解出明文。

客户端 vk_wrap/recovery_wrap/item blob 是服务端不解密的不透明材料；Java 不得解包其 Vault Key，不得接收主密码、Secret Key、明文条目。邮箱是服务端为通知可解密的特殊字段；禁止把数据库实体/Envers 审计自动序列化暴露这些内部字段。

## 6. SRP 字节级契约（不得猜算法）

实际依赖 `srp 0.6.0`，群=RFC 5054 3072 bit N，g=5，H=SHA256。N 的权威字节为该依赖 `groups/3072.bin`；选群不能只按“3072”标签。identity=account_id 原样UTF-8，口令=AuthKey **原始32字节**（不是hex/Base64，不是主密码）；AuthKey由客户端双因子KDF派生。正常随机 a/b 各64B。

记 `BE(x)` 为 BigUint 最短无符号大端编码（不加符号0、不统一左补384B）；H 输出当作无符号大端整数参与运算：

```text
x = H(salt || H(I || ':' || AuthKey))
v = g^x mod N
k = H(BE(N) || leftPadTo384(BE(g)))
A = g^a mod N
B = (k*v + g^b) mod N
u = H(BE(A) || BE(B))
S_server = (A * v^u mod N)^b mod N
S_client = (B - k*g^x mod N)^(a+u*x) mod N
M1 = H(BE(A) || BE(B) || BE(S))
M2 = H(BE(A) || M1 || BE(S))
```

`process_reply` 会从输入字节构造 BigUint，再用最短编码计算 proof。**u 没有 PAD(A)/PAD(B)**，即便依赖注释写了PAD；**key() 为 BE(S)，不是 H(S)**。M1 不是 `H(H(N) XOR H(g) | H(I) | salt | A | B | K)` 版本。Java BigInteger 必须显式无符号，并去掉正数符号前导0。A mod N=0 或 B mod N=0拒绝；proof不匹配拒绝。M1/M2各32B，按 DTO STANDARD Base64 传输。

## 7. 可执行黄金向量与验收边界

测试文件内固化 expected 字符串，不是在测试运行时用同一个函数临时计算 expected 再比较。来源是此 Rust 基线输出；不能称为 Java/其他语言独立验证。密封盒用已有 HKDF/AES-GCM 原语固定随机输入构造，和生产 `sealed::open`、`ServerKeys::decrypt_email/open_handshake` 双向格式核对，不给生产 API 添加固定随机数入口。

### 固定测试输入

- server_secret、SRP AuthKey：字节 `00..1f`（32B）。
- SRP salt、密封盒 salt：`20..3f`（32B）。
- 密封盒 IV：`40..4b`（12B）。
- account_id/handshake_id：`00000000-0000-4000-8000-000000000001`。
- device_id：`00000000-0000-4000-8000-000000000002`。
- SRP a=1（一字节01），b=64个22；故 A=05（Base64 `BQ==`），特意检测错误的PAD规则；这种a不是生产随机值。
- 邮箱输入 `  ALICE@Example.TEST\n`，规范化 `alice@example.test`；OTP=`000123`。

### 关键固定输出（STANDARD Base64）
