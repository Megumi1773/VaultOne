### 5.1 安全与正确性收口

- 已有保险库即使丢失/过期隐私标记，也不能发起业务网络请求；门面逐次读取持久化同意，覆盖直接页面调用。锁定在 await 前清空界面状态并撤销会话代次；敏感路由/弹窗销毁，晚到结果不回填。
- 保存位置对话框在锁定后返回，即使页面还没到下一帧销毁，也不写 CSV；恢复套件生成及保存位置返回后同样检查会话。已开始的操作系统写入不能靠界面状态撤回，本轮未宣称可取消已经开始的写入。
- SQLite 0003 恢复 12 个时间列非空约束，全程不关闭外键；测试覆盖全部旧表数据、索引、高水位、失败回滚与重启。PG 迁移入口固定专用连接 UTC，但不猜测修复已错误转换的历史值。
- 冲突原信封/版本与候选加密持久化，待裁决暂停该条目推送，旧候选/旧 ACK 不覆盖新内容。裁决后再次编辑/删除/恢复会保存旧裁决并产生新候选，不拿后续改动冒充原裁决已确认。
- 活动冲突阻止主动断连/云注销，避免切断 ACK 通道后永久卡住。无活动冲突时保留原先离线/401 也能本机断开的语义，云 DELETE 失败不假报成功。低频维护操作持本机 SQLite 写事务等待 HTTP（现有超时 20 秒），这是明确例外，不推广到 Java 服务端或普通同步；不能撤销已经在云端执行但响应丢失的动作。
- 服务端同账户推送在同事务内串行至提交；合法重试不重建历史或移动游标，元数据不同不再误报幂等成功。SQLite 真实 TCP 回归通过；PG 的受控交错测试已接 CI，但本机未执行。

### 6.4 配置内联、默认环境声明与开发库补齐（2026-10-01）

用户要求 Java 后端配置不再从环境变量加载、直接内联在 YAML，并补齐缺失项。已实施：

- 三个 YAML 去掉全部 `${...}` 占位。**分层口径**：公共 `application.yaml` 只放与环境无关的结构性配置（连接池、TTL、请求预算、日志、限额、UTC 时区、优雅停机）；连接地址与角色、服务端密钥、Redis 地址与命名空间、Flyway 角色全部由环境文件提供。
- **默认环境写在根 YAML**：`spring.profiles.active: dev`。环境选择本身也是配置，不再依赖 `SPRING_PROFILES_ACTIVE`；生产部署显式覆盖为 `prod`，`DeploymentGuard` 仍拒绝 dev+prod 同时激活。
- 补上的缺项：`vaultone.server-secret`（dev/prod 各一份 64 位十六进制、互不相同）、`spring.datasource` 地址/角色/口令、`spring.flyway.user`/`password` 与 `runtime_role`/`migrator_role`、prod 的 `server.ssl.certificate`/`certificate-private-key`/`enabled-protocols`、prod 的 `vaultone.mail.smtp-*`、`vaultone.redis.password` 与 `vaultone.ops.log-directory`。
- `spring.flyway.url` 刻意不写：迁移地址沿用 `spring.datasource.url`，只切换角色。首轮改动写死了该键，导致覆盖数据源的 `JettyVirtualThreadsTest` 与 `YamlConfigRegressionTest` 触发“Flyway必须与运行连接指向同一数据库”，已按此口径修正。
- 本机新建独立开发库 `vaultone_java_dev`（owner 为 `vaultone_java_migrator`）与受限运行角色 `vaultone_java_runtime`（均 NOSUPERUSER / NOCREATEDB / NOCREATEROLE / NOINHERIT / NOBYPASSRLS）。**未使用 Rust 服务端在用的 `vaultone` 库，也未使用本机管理角色 `root`。**

## 12. 2026-10-02：回收站彻底删除 / 清空

承接 §11 提交 `6b5f904` 之后。docs/09 §3「彻底删除 / 清空回收站」此前记为缺失（FRB、UI、内核三处无 `purge`/`empty_trash`），本轮补齐为主线 P1 项。**只改客户端与内核，不改协议、不动 Java/Rust 服务端。**

### 12.1 语义边界（决定实现范围）

现有删除是软删除：`delete_item` 置 `deleted_at` 并留 `dirty=1` 墓碑，由同步推给服务端，服务端同样保留墓碑。因此「彻底删除」在本机是**不可逆物理抹除**——删掉本机密文行即无法再解密其内容，**不会也不能**通知服务端在别处抹除已同步的数据。UI 二次确认如实说明「已同步到云端的数据不会在其他设备上被抹除」，不暗示云端联动删除。

- 仅接受回收站条目（`deleted_at IS NOT NULL`）；对活动条目报 `not_found`。
- 要求该条目的删除已同步（`dirty == 0`）：未同步的墓碑直接抹除会连带丢弃本机未推送的修改，下次同步还可能把服务端旧内容重新拉回。未同步返回新稳定错误码 `item_unsynced`，UI 提示「请先完成同步后再彻底删除」。清空回收站逐条执行同一规则，未同步的保留并在结果中报告保留数。
- 物理删除整行（含密文 blob 与墓碑）；`secure_delete=ON` 覆写旧页，不留残留。不产生任何待推送记录（`pending_changes` 不变）。
- 活跃冲突条目的本机行可被抹除，其冲突记账随之失效（`dirty_items` 已按冲突存在性过滤，孤儿无害）。

### 12.2 实现

- 内核 `crates/vault-core`：`store.rs` 新增 `purge_item`（`DELETE ... WHERE id=?1 AND deleted_at IS NOT NULL`，返回受影响行数）；`error.rs` 新增 `VaultError::ItemUnsynced` → `item_unsynced`；`vault.rs` 新增 `purge_item`（会话校验 + 回收站/同步前提 + 事务内 `check_item` 完整行 CAS 后抹除）与 `empty_trash`（逐条同规则，返回 `(已抹除, 保留)`）。
- FFI `app/rust/src/api/vault.rs`：`purge_item`、`empty_trash`（返回 `EmptyTrashResult{purged,kept}`）；`flutter_rust_bridge_codegen generate` 重新生成，未手改生成物。
- Dart：`VaultApi.purgeItem`/`emptyTrash`（`_session` 包裹）；`AppState.purge`/`emptyTrash`（`_withSession` + `refresh`）。
- UI：`item_detail.dart` 回收站分支在「恢复」旁增「彻底删除」（danger），复用 `confirmDialog` 二次确认，`purgeErrorMessage` 按稳定 code 给安全中文提示；`home.dart` 回收站分区在列表标题行（桌面 `ItemListPane.headerAction`）与手机 `AppBar` actions 提供「清空回收站」，空回收站不显示。

## 14. 2026-10-02：国际化基础设施与语言切换

承接 §13 之后，推进 docs/09 的 P1「国际化」第一段。**只改客户端，不动协议与服务端。**

### 14.1 设计取舍（为什么不引 `.arb` + gen-l10n）

`.arb` + `flutter gen-l10n` 会给 851 处文案引入生成代码、构建步骤与「键名 ↔ 文案」两套标识，而本项目的文案需要按页分批迁移、且必须能在漏翻译时**回退中文原文**而不是露出键名。因此选择集中式文案表：

- 常量本身是**简体中文原文**（`AppStrings.settings = '设置'`），可直接当默认语言使用，不额外维护键名。
- `AppStrings.translate(source, language)` 查表覆盖；缺条目回退原文，**漏翻译不会显示空白或键名**。
- `LocaleScope`（InheritedWidget）+ `context.tr(...)` / `context.trf(...)` 取词；没有 `LocaleScope` 时回退默认语言，独立页面与既有测试不需要改造。
- 语言进 `Settings.language`（持久化键 `language`），随 `MaterialApp.locale` 与 `supportedLocales` 生效。

- `settings_page.dart`：外观分区新增「语言」行（三语 `SegmentedButton`）；全部 14 个分区标题与页面大标题改走 `context.tr`。

## 16. 2026-10-02：层级分类与分类树（docs/09 §3.6 / §3.11）

### 16.1 设计取舍：分类即层级，树从条目派生

新建独立的分组实体需要新表、新的同步实体，并同时改 Rust 服务端与 Java 服务端的协议与迁移——那是一次跨两台服务端的契约变更，风险远大于收益，且会长期占用两套迁移。

这里改用**让分类本身就是层级路径**（`工作/生产/服务器`）：分类字段已经贯通同步、三方合并、冲突裁决与 CSV 导入导出，因此层级是零协议改动拿到的，且天然多设备一致。

代价如实记录：**空分类不会存在**（没有条目就没有节点），也没有分组级元数据（图标 / 颜色 / 自定义 sortOrder），§3.11 的「首页板块按 sort 排序」仍缺失。

## 17. 2026-10-02：安全体检系统（docs/09 §5.2）

### 17.1 结构：规则在内核，展示在界面

新增 `crates/vault-core/src/health.rs`，是一段**纯函数**：输入是已解密条目、泄露检测结果、
设备环境探测与安全设置快照，输出可直接展示的报告。设备探测留在 `app/rust`（平台层），
内核不碰平台 API——因此这套打分规则可以在任何平台上完整单测，界面也不必重算任何口径。

### 17.2 评分口径（写死并可复核）

总分 = `100 - min(100, 各维度扣分之和)`；每个维度有独立上限，互不挤占：

- 泄露 50（单次 25）、弱密码 24（6）、复用 20（5）、长期未更新 15（3）、
  设备环境 30（6）、设置项 30（10）。

单次扣分取「上限 / 4」量级：约四项饱和，既让严重问题立刻反映，也不至于一条弱密码
就把总分打穿。调整规则必须同步改内核测试与本文件。

### 17.3 几个刻意的判断

- **没查过不能算失分**：泄露检测未运行或不可用时给出提示但**不扣分**，该维度标记为
  「跳过」；用户主动跳过则既不扣分也不提示。界面上跳过的维度明确显示「本次跳过」，
  避免让人误以为「这一项没问题」。
- **长期未更新只看密码何时设置**（`password_history` 里最近一次改密时间，无历史则用
  `created_at`），不看条目何时编辑——否则改个标题就绕过了体检。有测试固定这一点。
- **发现项 id 稳定**，因此忽略（snooze）能跨次体检生效；忽略只影响提示，不影响分数。
- **环境探测只做真能做的**：Windows 上调用 `IsDebuggerPresent`（kernel32 默认已链接，
  不需要新依赖）；模拟器 / ADB / 开发者选项 / root 在桌面端没有意义，如实填 false；
  锁屏状态无法可靠判定，保守填「安全」以免误报。不支持的平台整维跳过。
- **不可读条目如实计入**，不假装扫描完整。

### 17.4 界面

安全页从「自己算分」改为消费内核报告：分数环 + 检查时间 + 过期提示、六维进度条
（含扣分/上限与跳过标注）、扫描统计、发现项列表（严重度标签、下钻展开关联条目、
执行动作、忽略 7 天与一键全部恢复）。

页面依赖全部由外部注入（`items` / `settings` / `runCheckup` / `loadSnoozes` /
`saveSnoozes` / `onOpenItem` / `onOpenSettings`），沿用本仓库其他页面的做法，
因此可以脱离全局单例单测。忽略记录存在本机设置 `health_snoozes`（非敏感、不同步）。

界面收敛掉一处含混设计：「已忽略 N 项」原为「先展开、再清除」的两段式，按钮文字不变

## 18. 2026-10-02：安全总览（docs/09 §5.1）

### 18.1 不新增第二套判定规则

任务清单的完成态**全部取自 `checkup` 已经用过的同一批事实**（设置快照 + 体检报告），
`checklist()` 只是把它们组织成「可勾选的清单」。若另写一套判断，「设置页说已开启、
总览说未完成」这种自相矛盾迟早会出现。

清单项：自动锁定、退出时锁定、剪贴板自动清除、关闭详细诊断日志、运行泄露检测、
没有已泄露的密码、没有弱密码、没有重复使用的密码、设备环境无风险；**设备支持生物识别时
才插入生物识别项**——不支持却列出来，用户永远做不完。

两处刻意的判断：

- **没跑过泄露检测既不算完成也不算失败**：「运行泄露检测」与「没有已泄露的密码」都标未完成，
  但不会因此扣分。把「没查过」当成「没问题」是这类体检最常见的自欺。
- **清单项不使用 `openItem` 动作**：清单项不携带条目，`openItem` 会变成一个没有目标的按钮。
  密码类任务统一指向体检详情，要改哪几条在那里逐条列出。内核测试固定了这一点。

`SingleChildScrollView` 一次性布局后深链始终有效。设置页一共十几个分区，这个代价可以接受。

## 19. 2026-10-02：首页板块自定义与板块排序（docs/09 §3.6 / §3.11）

### 19.1 范围

基线 §3.6 的「首页板块自定义页（板块排序、显示/隐藏、是否展示）」与 §3.11 的
「首页板块按 sort 排序」是同一件事：让用户自己决定侧栏有哪些分区、按什么顺序排。
设置页新增「首页板块」分区，可上下移动、逐项显隐、一键恢复默认。

### 19.2 为什么不同步

布局存在本机设置 `sidebar_layout`（JSON），**不进同步**。不同设备屏幕大小不同，
在手机上隐藏的分区在桌面上可能正需要；把布局同步过去只会让两边都不顺手。
状态层只存这段不透明字符串，由界面用 `resolveSidebarLayout` 解释，保持分层。

### 19.3 解析容错（这一块才是真正的风险点）

设置可能来自旧版本、被手改或损坏，所以 `resolveSidebarLayout` 一律**优先可用**：

- 空值、非 JSON、非数组 → 回退默认布局。
- 未知 id 直接丢弃（可能来自被降级的版本，留着只会渲染不出来）。
- 重复 id 只保留第一次。
- **缺失的分区按默认顺序补到末尾**——否则升级后新加的分区会直接消失，用户找不到入口。
- `settings` 不在可排序分区里（它固定在侧栏底部），即使被写进布局也会被挡掉。

还有一条：**不允许把最后一项可见也关掉**。侧栏变成一片空白后，用户没有恢复入口；
`canHide` 因此被单独测了四种情形。

分组标题按首次出现的位置渲染（布局里只存 group key，取词留给界面），
所以拖动条目时标题会跟着走，不会出现「标题下面没有条目」。

## 21. 2026-10-02：导入预览、字段映射与覆盖策略（docs/09 §3.7）

### 21.1 覆盖策略：Skip 的语义刻意不动

三种策略里只有 `Skip` 与既有行为完全一致（**只按内容去重，不按标题去重**），另外两种只在
标题相同时才有区别。这样新增选项不会悄悄改变老路径的行为——这一点在测试里明确写出来，
因为「Skip 不按标题去重」是很容易被后来的改动顺手改错的地方。

- `Overwrite`：按标题不区分大小写匹配同名条目，覆盖内容但**保留其 ID 与创建时间**——
  覆盖的是内容，不是身份。
- `KeepBoth`：同名条目加「标题 (2)」递增后缀另建。
- 内容完全相同的条目在任何策略下都算重复跳过：`Overwrite` 不该把一条一模一样的记录再写一遍。
- 无效条目（如 TOTP 密钥非法）在覆盖策略下也**不覆盖**有效数据，只计入 `invalid`。

### 21.2 预览与字段映射

内核 `import::preview` 返回：识别格式、CSV 表头、前 20 行原始数据、总行数、解析出的条目、
跳过数、**逐条可读的警告**、当前列映射、未被使用的列。

`ColumnMapping` 是可序列化的值对象，界面改完下拉框**把新映射回传内核重新解析**，
而不是在 Dart 里另写一套列取值逻辑——否则别名表就有了第二份真相。

警告覆盖四类：格式错误的行、没有可导入内容的行、TOTP 无法识别已降级为敏感自定义字段、
未被使用的列。最后一条是这次新增的：自制 CSV 里最常见的失败就是「列名认不出来，数据静默丢失」，
点名未使用的列能让用户立刻知道该去改映射。

预览对话框**只展示原始列，不展示解析后的密码**：预览的目的是核对列对应关系，不是看明文。

## 22. 2026-10-02：标签与分类的批量管理（docs/09 §3.6）

### 22.1 四条规则与它们各自的理由

- **标签匹配不区分大小写**：与 `normalize_tags` 的去重口径一致。否则 `Work` 会漏掉，
  而用户根本分不清「Work」和「work」为什么是两个标签。
- **`rename_category` 是前缀改写**：`工作` → `职业` 会把 `工作/生产/服务器` 一并变成
  `职业/生产/服务器`。只改完全相等的那一条会让所有子分类变成孤儿。
- **拒绝把分类移到自己的子分类下**：`工作` → `工作/子` 会让派生树成环。这个判断在内核里，
  不是只在界面上拦一道。
- **清空分类不删条目**：用户说「删掉这个分类」时想删的是分类，不是里面的密码。测试里明确
  断言条目数不变。

改成已存在的标签/分类等于合并，这是免费得到的——规范化本来就会去重。

### 22.2 批量改写只有一条写路径

四个操作统一走 `rewrite_items` → `update_item`，因此版本号递增、`updated_at` 推进、
`password_history` 保留、同步语义全部与手动编辑完全一致。**批量管理不应该有第二条写路径**——
否则「批量改过的条目同步不过去」会成为一个极难定位的问题。测试断言：命中的条目
`revision` 加一且 `updated_at` 推进；**未命中的条目一个字节都不动**。

### 22.3 测试抓到一个真实缺陷

`_askName` 原本在 `showDialog` 返回后就 `controller.dispose()`。退场动画还在跑、`TextField`
仍持有控制器，于是抛 `A TextEditingController was used after being disposed`。这不是测试
环境的产物，生产里同样会炸。改为让弹窗自己是一个 `StatefulWidget`，控制器由它持有并在自己的
`dispose` 里释放。**这类「await 之后立刻释放」的写法在别处也要留意。**
